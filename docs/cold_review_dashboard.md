# OAM Dashboard — Cold Review

*Independent review by a fresh agent with no prior context on this project — repo (through the CxG work) and the live deployed dashboard reviewed separately.*

## Overall Verdict

**Current state: 5/10 as a shipped portfolio piece. Potential: 8/10 if the punch list below gets executed.**

The gap between the two numbers is the story here. The engineering underneath — BigQuery cost hygiene, auth reliability, test discipline, honest disclosure of a losing model — is genuinely senior-level and better than most portfolio projects I review. But the thing a hiring manager actually clicks through in 90 seconds is unfinished: a fabricated Overview page with no "demo data" label, three dead links/buttons on the pages a recruiter would hit first, a literal "Not yet built" placeholder live in production, and a metric-selector control that does nothing at all. A recruiter giving this the stated 60–90 second look bounces on the Overview page before ever seeing the good engineering underneath — the parts that would actually get this candidate an interview are gated behind a click depth most visitors won't reach.

Two things pull the code-side score up sharply from what the project's own design doc would lead you to believe: the doc's own "hard gate" status table is stale in the codebase's favor — three of four blocking issues it lists as unresolved (TTL caching, RoleProvider timeout, BigQuery client singleton) are actually fixed and tested. That's a good sign about engineering velocity, but it means the doc itself is now a slightly misleading artifact if a technical reviewer reads it as ground truth.

## Code-Level Findings

**Architecture.** Clean separation: FastAPI routers (`src/opponent_adjusted/api/routers/*.py`) sit behind Protocol-typed store interfaces resolved via `Depends()`, concretely implemented by `BigQueryServingStore` / `BigQueryAnalysisStore` / `BigQueryCxgCoverageStore`. Frontend mirrors this discipline: `web/lib/api.ts` centralizes fetches behind a typed `ApiError`, and `web/lib/nav-config.ts` is a genuine single source of truth driving both the rendered nav and route gating (`isRouteAllowed()`, consumed by `RoleGate.tsx`). No stray `bigquery.Client()` construction paths — confirmed lazy singleton, with a dedicated regression test (`tests/api/test_bigquery_client_singleton.py`).

**Cost discipline — the standout strength.** `bigquery_store.py` wraps all nine `BigQueryServingStore` methods in `TTLCache` (300s, cachetools), directly citing the real ~£2.50/34-query/6.1GB incident in its own code comments as the reason it exists. More significant: while building this, a second, undocumented bug was caught and fixed — `oam_core`'s silver tables carry three lineage-versioned copies per row, and none of the original nine queries filtered on `silver_schema_version`, meaning every Explore-zone aggregate was silently 3x-inflated before the fix. That's the kind of bug that's easy to ship and expensive to notice; catching and regression-testing it (`tests/api/test_bigquery_store_lineage_filter.py`, 10 tests) is a real credibility signal for a data scientist reviewer, arguably more than the CxG model itself.

**Design-spec drift (doc problem, not code problem).** `docs/dashboard_design_spec_v2.md` §9 lists hard gates 4 and 5 as "blocked" — they're not. Gate 4 (TTL cache) and gate 5 (RoleProvider `/v1/me` timeout, `web/components/shell/RoleProvider.tsx` lines 27–43, 9s `AbortController`-style race with a `finally` that unconditionally resolves) are both implemented and covered by tests that postdate the doc's status line. Gate 3 (signed GCS URLs) is also built (`src/opponent_adjusted/api/gcs_signing.py`) and correctly falls back to raw text on failure — it's blocked only on an IAM grant (`roles/iam.serviceAccountTokenCreator`), a one-line `gcloud` command, not a build task. Only gate 2 (`oam_serving`, zero tables, no Track B quadrant scatter anywhere in the codebase) is genuinely blocked as described. **Fix the doc, not the code** — as written it undersells work that's already done, which matters if a technical reviewer treats it as ground truth (its own stated purpose).

**CxG implementation matches spec intent, with two real gaps.** Coverage gating is real, not cosmetic — `cxg_coverage.py`'s `get_cxg_for_events()` returns values only for event_ids inside the v3 test split, with no placeholder for the rest, and this is honestly reflected in the frontend caption `"57 of 220 shots have CxG coverage (experimental)"` on player/match pages. Table names are exactly as spec'd (`oam_ml.cxg_event_v3_predictions`, `oam_ml.cxg_plus_v3_predictions`, never `oam_serving`). Two gaps: (1) the "Experimental" disclosure only exists as a native hover `<title>` tooltip on `PitchMap.tsx` plus a small caption line — not a persistent visible badge, weaker than the spec's stated intent; (2) **Teams pages have zero CxG anywhere** — no `PitchMap`, no coverage caption, nothing — despite the spec explicitly listing Teams as one of the three Explore-zone surfaces where CxG should appear.

**The Overview page is the sharpest finding in the whole review.** `web/app/overview/page.tsx` is 100% hardcoded fabricated data: `Team CxG 1.82`, a `DEMO_SHOTS` array of five made-up shots, a `Leaderboard` with hardcoded values and two rows permanently rendered as loading skeletons that are never wired to a real fetch, and a static SVG `ProfileRadar` with zero data binding. None of it is labeled as demo/placeholder data. This is a real inconsistency against the project's own stated value ("disclose, don't fake" — the exact principle it applies correctly to the CxG-vs-StatsBomb comparison) landing on the one page recruiters are told to look at first.

**Test coverage is genuinely strong, not scaffolding.** ~118 tests in `tests/features/cxg/` (the best-covered area), ~82 in `tests/api/` covering routers plus every named fix above, 10 Vitest files in `web/tests/` (598 lines) targeting exactly the risk areas that matter — role resolution, admin leakage, pitch-map rendering. Gaps: no tests for the Overview page's mock content (arguably appropriate, given it should be deleted rather than tested), no direct tests of `web/lib/api.ts`'s fetch/error handling, and `bigquery_analysis_store.py` has several unfiltered full-table scans (`list_bivariate_candidates`, `list_pca_components`, etc.) — low risk since they're `require_admin`-gated against small pre-aggregated tables, but inconsistent with the discipline applied everywhere else in the same file.

## Live-Dashboard Findings

**Overview (`/overview`)** — Landing page, and the weakest page on the site. Four metric tiles, one of which (`Team CxA`) renders completely empty with no label explaining why. A shot map with exactly 4 shots. A leaderboard showing 3 real-looking rows and 2 permanently blank rows (4 and 5). A "Profile radar" that's just an empty pentagon outline — no data, no legend. None of it is labeled as sample/demo content, which matches the code finding above. This is what a recruiter sees first, per the design spec's own stated persona intent, and it currently undersells everything else on the site.

**Matches (`/matches` + detail)** — The strongest page on the site. 610 real matches across three competitions, filterable, with a genuinely well-built detail page (real shot map, real lineups, real xG per team) when opening Peru–Denmark and Arsenal–Swansea. **However: the "Metric" selector (xG / CxG / CxA / CxT) in the left sidebar is completely non-functional.** Confirmed two ways — clicking "CxG" changes nothing visually (headers stay "Team xG," shot map stays the same), and an interactive-element scan of both the list and detail pages shows **zero** interactive elements under "Metric" at all; the boxes aren't wired to anything, not even broken JS — they're static decoration. This is a real, confirmed dead control sitting front-and-center on the site's best page, and it directly blocks the one feature (CxG toggle) the whole project is built around.

**Players (`/players` + detail)** — 1,457 players, real data, but the list table has **no column headers** — numeric columns (shots/goals/xG, e.g. Harry Kane: 220/42/35.97) are unlabeled, so a first-time visitor has to guess what they mean. Detail pages are sparse: a shot map and three stat tiles, no leaderboard, no radar despite those being advertised Explore-zone components. The CxG coverage caption does render correctly here ("57 of 220 shots have CxG coverage (experimental)"), but the shot map itself is a dense, unlegend-ed overlapping cluster of circles for high-volume players (Kane's 220 shots) — no zoom, no color-key for goal/miss or team, which will read as visually noisy rather than analytical to a non-technical visitor.

**Teams (`/teams` + detail)** — Same missing-headers issue as Players. Detail page is the thinnest of the three Explore pages: three stat tiles and a match list, no shot map, no CxG at all (matches the code finding). Also mixes club teams and national teams in one ranked list (Leicester City next to Spain/England/France) with no filter to separate them — analytically confusing since they're not comparable populations, and there's no toggle to fix it.

**Stories (`/stories`)** — Five well-titled cards, one specifically and honestly framed ("CxG v3 — an honest comparison against StatsBomb xG... trails the baseline, and that's a legitimate, disclosed result, not a hidden one"). **All five cards are dead — non-clickable, no navigation on click, confirmed via direct interaction.** This is the exact content a data-scientist persona is told (by the spec itself) to come here for, and it's a page of headlines with no bodies.

**Models (`/models`)** — The best "Understand" page. Real numbers, correctly labeled "Evaluated" (not "Validated"/"Production"), explicit trailing-the-baseline disclosure with real log_loss numbers. **The "See Stories for the full comparison →" link is also dead** — confirmed via click, stays on `/models`. Two "Planned" cards (CxA, CxT) are honestly labeled rather than faked, which is good practice, but sit oddly next to Overview's unlabeled fake CxA tile — inconsistent within the same product.

**About (`/about`)** — Literally renders "About / Not yet built" with an empty skeleton box, live in production. This will read to any visitor as an abandoned or half-shipped project the moment they click it, regardless of what else is good.

**Analysis (admin-gated)** — Correctly redirects an unauthenticated visitor to `/overview` rather than hanging — confirms the RoleProvider timeout fix works in practice, not just in tests. No console errors observed on any page visited (Overview, Matches list/detail, Players, Teams, Stories, Models, About, Login).

**Login (`/login`)** — Clean, on-brand, functional-looking (Google, email/password, "Continue as guest"). Not tested end-to-end (no credential entry, per review scope), but nothing here reads as broken.

## Prioritized Fix List

1. **Kill or clearly label the Overview page's fake data.** Highest impact, lowest effort. Either wire it to the real "recent matches" live strip the spec already calls for, or slap a visible "Sample data" badge on every tile until it is. This is the single highest-leverage fix because it's the first thing every visitor type sees, and it's currently the site's biggest credibility risk given the project explicitly brands itself on honest disclosure.

2. **Fix or remove the Matches-page Metric selector.** It's dead UI on the site's strongest, most-clicked page, sitting right where a technical visitor would expect to toggle the flagship CxG feature. Either wire it to actually call `getCxgCoverage` and swap displayed values/badges, or remove the CxG/CxA/CxT boxes until it works — a visibly broken control is worse than no control.

3. **Make Stories cards and the Models "See Stories" link actually navigate.** Both are one Next.js `<Link>` away from working — `StoryCard.tsx` renders a `<div>` with no `href`. This is the exact content path a data-scientist persona is told to follow, and it currently dead-ends twice in a row.

4. **Add CxG to the Teams detail page.** Small, contained fix (mirror what `matches/[matchId]` and `players/[playerId]` already do) that removes an inconsistency the spec itself calls out as intentional scope ("Matches, Players, Teams").

5. **Add table headers to Players/Teams list views.** Cheap fix, removes the "what do these three numbers mean" guesswork for a casual visitor.

6. **Replace the About page's placeholder with the spec's intended content** (data source, versioning, glossary) — even a short version is better than a live "Not yet built" screen, which actively damages first impressions regardless of everything else being fixed.

7. **Update `dashboard_design_spec_v2.md`'s hard-gate status table** to reflect gates 3–5 as done. Low effort, but matters specifically for the data-scientist persona this document is aimed at — an out-of-date "here's what's broken" doc undermines exactly the credibility signal the project is trying to build.

8. **Grant the missing IAM role** (`roles/iam.serviceAccountTokenCreator`) to unblock signed GCS URLs for the Analysis tab charts — one command, unblocks a whole admin-tab feature that's otherwise fully built and tested.

9. **Persistent CxG "Experimental" badge instead of hover-only tooltip.** Lower priority since the caption text already does the disclosure job, but a hover-only native tooltip is easy to miss and weaker than the spec's stated "visible badge" intent.

10. **Separate club vs. national teams in the Teams leaderboard**, or add a competition-type filter — minor, but currently produces a ranking that doesn't mean anything analytically.

Items 1–3 are all small, contained frontend fixes (probably under a day combined) that would move the honest verdict from 5/10 toward the 7–8 range on their own, because they fix exactly the things a recruiter or technical reviewer would notice in the first two minutes. The backend engineering doesn't need defending — it already reads as strong; the frontend polish is what's currently costing this project the first impression it deserves.
